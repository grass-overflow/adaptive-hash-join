# Novelty: bounded proportional chunks with packed coarse work

The proposed project contribution is an explicit budget on the number of fine-grained probe chunks, independent of the total scheduled-task count. The original `novelty_budgeted` policy is retained as the unbatched variant. `novelty_packed` is the adaptive implementation: it activates budgeted chunking and coarse batching only when maximum-to-average partition imbalance is at least `packing_imbalance_threshold` (default 16). Below that threshold it falls back to unsplit coarse dynamic tasks. When active, it batches up to `coarse_batch_size` (default 8) non-selected non-empty partitions into one coarse task.

1. Count probe tuples in every radix partition; average includes empty partitions.
2. Mark a non-empty partition as oversized when `|S_i| > f * average`, with default `f=2.5`.
3. Rank candidates by descending probe count, breaking ties by partition number.
4. Set the fine-chunk budget to `B = T*q`; the default `q=32`, so four workers imply a budget of 128 chunks.
5. For `novelty_packed`, first require `max_i |S_i| / average(|S_i|) >= 16`; otherwise leave all partitions unsplit and unbundled. This imbalance gate is separate from the candidate rule and is a guard against scheduler/packing overhead when skew is modest. When enabled (or for the always-on `novelty_budgeted`), select candidates in rank order while there is room for at least two non-empty chunks per selected candidate. Initialize each selected partition with two chunks; distribute remaining budget proportionally to partition sizes, using deterministic largest-remainder apportionment and respecting the maximum of one chunk per tuple.
6. Divide selected probe ranges into contiguous, non-empty chunks that cover each tuple exactly once. In `novelty_budgeted`, non-selected non-empty partitions remain individual coarse tasks. In `novelty_packed`, consecutive unselected partition ranges are bundled, including any intervening empty partitions, and the bundle contains at most the configured number of non-empty partitions. Selected partitions break bundles. A bundle is still a coarse task: its partitions are processed serially by one OpenMP worker.
7. Consume the combined coarse bundles and fine chunks with OpenMP dynamic scheduling.

The budget applies to fine chunks only. Coarse tasks can make the total scheduled task count exceed the budget. Coarse bundling reduces scheduler dispatch count, but changes the granularity and may reduce load balance if bundled partitions differ greatly in size. If the budget is less than two chunks, no partition is split. If candidate sizes cannot consume the full budget without making empty chunks, the unused budget remains unused. The scheduler exposes its task plan for exact coverage and budget tests. The imbalance threshold is a configurable heuristic, not a proven optimum; its selection and held-out evidence are documented separately.

This differs from the paper-style baseline: the novelty chooses *which* candidates to split and apportions a bounded chunk count in proportion to their sizes; the packed version additionally gates that work on observed imbalance and coalesces small partition work to reduce queue dispatches. Both `--pack-threshold` and `--coarse-batch` are configurable. These are heuristics and must be validated on new workloads and machines. It does not claim to implement CAS-aware work stealing, custom deques, cache-migration estimates, hardware cost calibration, or cost-gated steals. OpenMP's dynamic loop scheduler is used as-is.

The task planner does not model `alpha*|R_i| + beta*|S_i|`, since the implemented chunk tasks only subdivide probing after one local hash table has been built for each partition. `split_factor` and the packing imbalance threshold are observed-size criteria, not a calibrated cost model. Results should state this scope precisely.

The current coarse packer groups consecutive unselected partitions by count rather than by estimated work. `results/adaptive_batch_tuning.csv` shows that task-count reduction is not monotonic with runtime as the batch size changes. Size-aware bundling—isolating unselected oversized candidates and grouping the remaining partitions by tuple-count load—is a future-work hypothesis; it has not been implemented or measured.

The q=64 high-skew confirmation (`results/robust_q64_confirmation.csv`) shows that fewer tasks and better worker probe-load balance can coincide with a lower probe time versus static/coarse-dynamic scheduling without improving end-to-end time versus the strongest fine-grained baselines. Report this measured boundary explicitly; do not generalize the probe-phase result into an overall join speedup.
